# Стандарт випуску релізів

## 1. Підготовка

1. Визначити повну версію продукту.
2. Визначити відповідний Git-тег.
3. Оновити CMake, runtime-тег, документацію, `CHANGELOG.md` і ROS-маніфести.
4. Переконатися, що зміни виконані в робочій гілці та мають зрозумілі коміти.

## 2. Передрелізний gate

1. Виконати всі перевірки зі
   [стандарту передрелізного тестування](PRE_RELEASE_TESTING_UK.md).
2. Зберегти версію Docker base image, SHA коміту й результати тестів.
3. Зберегти версію, URL і SHA-256 пакета IROS2_0; для поточного релізу це `0.1.1-1+deb13`.
4. Зберегти зафіксований Git SHA `cv_bridge`, якщо компонент не входить до пакета IROS2_0.
5. Не створювати та не пересувати тег, доки test gate не пройдено.

## 3. Формування артефактів

1. Зібрати Debian 13 ARM64 `.deb` командою:

   ```powershell
   .\tools\build-arm64-deb.ps1 -Version 1.0.1.7
   ```

2. Перевірити ім’я, control metadata, вміст і SHA-256.
3. Перевірити точну залежність `iros2-0 (= 0.1.1-1+deb13)` і відсутність вбудованої копії ROS underlay.
4. Називати артефакт:

   ```text
   vins-mono-ros2_<PRODUCT_VERSION>_arm64.deb
   ```

5. Не перейменовувати пакет замість зміни його внутрішньої версії.

## 4. Публікація Git

1. Злити перевірений коміт у `main`.
2. Переконатися, що локальна і віддалена `main` синхронізовані.
3. Створити анотований тег на фінальному коміті.
4. Опублікувати `main` і тег.
5. Перевірити, що розіменований тег і `main` вказують на очікуваний SHA.

## 5. GitHub Release

1. Створити release з точним ім’ям Git-тега.
2. Додати витяг із `CHANGELOG.md`.
3. Завантажити `.deb`.
4. Опублікувати SHA-256 поруч з артефактом.
5. Перевірити пряме завантаження файла.

## 6. Перевірка після публікації

1. Завантажити опублікований файл, а не локальну копію.
2. Звірити SHA-256.
3. Встановити пакет на чисту підтримувану Raspberry Pi OS.
4. Виконати Raspberry Pi smoke-test зі стандарту тестування.
5. Задокументувати результат у release notes.

## 7. Відкат

Якщо перевірка після публікації не пройшла:

1. Позначити release як непридатний або draft.
2. Прибрати дефектний asset із публічного використання.
3. Не перевикористовувати той самий номер для іншого вмісту після широкого
   розповсюдження; випустити наступний `PATCH`.
4. Описати причину та виправлення в `CHANGELOG.md`.

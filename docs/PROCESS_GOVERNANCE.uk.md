# Управління процесом

Ця політика узгоджує ведення задач, релізів і доказів VINS-NEO з iROS2 та
iMAVROS, зберігаючи продуктові gate, специфічні для VINS.

## Облік роботи

Суттєва робота з реалізації, процесу, документації, пакування або релізу до
початку реалізації повинна мати одну відкриту GitHub Issue й одну ClickUp
task із взаємними посиланнями та затвердженим обсягом.

GitHub є джерелом істини для коду, комітів, pull request, тегів, релізів,
технічного обсягу, критеріїв приймання, журналів, контрольних сум, маніфестів
і незмінних доказів. ClickUp є джерелом істини для статусу планування,
власника, пріоритету, графіка, бізнес-обсягу, блокерів і координації між
компонентами.

Обидві задачі повинні визначати мету, обсяг і виключення, застосовну версію
продукту/процесу, упорядковані етапи, критерії приймання, ризики, залежності,
блокери та посилання на докази. Етап завершено лише після того, як його
перевірка створила стійкий доказ.

## Контрольні точки та продовження роботи

Фіксуйте контрольну точку після змін обсягу або версії, перевірених комітів,
результатів gate, змін блокера, фіналізації маніфесту, публікації та
післярелізної перевірки. Вона містить точний коміт, завершений і наступний
етап, виконані перевірки з явним результатом, посилання на докази та потрібну
дію власника.

Перед продовженням роботи порівняйте стан Git, GitHub Issue і ClickUp task,
щоб знайти останню перевірену контрольну точку. Не повторюйте пройдений gate,
якщо його входи й докази не змінилися. Не створюйте дублікати задач, коли
зв’язок неясний.

## Оцінки та час

До активної роботи ClickUp task повинна містити оцінку обліковуваної праці,
впевненість, ризики, очікуваний машинний час і зовнішнє очікування.
Використовуйте таймер ClickUp для активного аналізу, реалізації, review,
контрольованих збірок, перевірки, документації та публікації. Зупиняйте його
під час неконтрольованого виконання або очікування даних користувача,
облікових даних, обладнання чи зовнішнього погодження.

Переоцінюйте роботу після початкового аудиту, першої репрезентативної збірки,
суттєвої зміни обсягу чи блокера та перед release gate. Зберігайте початкову
оцінку й записуйте причину та доказ кожного перегляду.

## Стани тестів і доказів

Кожна запланована перевірка має рівно один результат:

- `PASS` — завершена, усі умови приймання виконано;
- `FAIL` — завершена, принаймні одну умову не виконано;
- `BLOCKED` — застосовна, але не завершена через відсутній вхід або середовище;
- `SKIPPED_NOT_CONFIGURED` — потребує обладнання, якого немає в затвердженій
  конфігурації цілі;
- `SKIPPED_NOT_APPLICABLE` — поза вибраним обсягом або продуктом;
- `NOT_RUN` — не запускалася й затвердженого пропуску немає.

Не називайте часткову, перервану за часом, пропущену або заблоковану роботу
`PASS`. Доказ містить ID тесту, результат, часові позначки, host, target,
точну команду, коміт коду, ідентичність залежностей/маніфесту, контрольні суми
артефактів за потреби, місце доказу та причину кожного результату не `PASS`.

Обов’язковий `FAIL` провалює gate. Обов’язковий `BLOCKED`, `NOT_RUN` або
непогоджений пропуск блокує gate. Звичайний `PASS` дозволений лише коли всі
застосовні обов’язкові перевірки пройдено.

## Релізний контракт

Релізний коміт повинен фіксувати точний вхід iROS2, використаний VINS-NEO, а
коли iMAVROS входить до вибраного інтеграційного обсягу — також точний вхід
iMAVROS. Кожен зафіксований вхід містить випущену версію, незмінний URL
артефакту, метадані пакета та SHA-256. Залежності обирають до релізного
коміту, а не під час збірки.

Офіційні ARM64-артефакти VINS-NEO збирають і тестують нативно на затвердженій
цілі Raspberry Pi 5 з Debian 13. Docker, емуляція, cross-compilation та інша
архітектура можуть допомагати діагностиці, але не є доказом нативного релізу.

Продуктовий тег створюють лише після проходження metadata gate, нативної
збірки, автоматичних тестів, аудиту пакета, чистого встановлення, runtime
smoke-test і dataset gate VINS. Після публікації завантажте опублікований
артефакт, перевірте контрольну суму, встановіть підтримуваним способом і
повторіть потрібний smoke-test. Теги й опубліковані версії незмінні.

## Завершення та блокери

Не закривайте GitHub Issue й не встановлюйте термінальний статус ClickUp, доки
не пройдено всі критерії та обов’язкові gate, не опубліковано фінальні коміти
й теги, не додано посилання на докази, версії та документація не відповідають
публікації, а термінальний запис не прочитано й не перевірено після зміни.

При блокуванні запишіть точний відсутній вхід, останню успішну контрольну
точку, решту обов’язкових пунктів і безпечну дію для продовження. Блокер не є
завершенням і не дозволяє послаблювати gate.
